# 编译舱 — na 自持编译+热更链（living，2026-09-23 立项）

> 用户拍板（2026-09-23）：「未来我启动旧手机，工具链等等还需要在那边开一个
> 完整的测试，那时候就需要 na 拥有自己的编译热更新链路，陌生的设备可没有
> 我们现在的 termux 资产。」本档是该项唯一设计源。

## 背景

- 2026-09-23 日常闸已收归服务器全天（AGENTS.md 跨线运维公约 1 修订，
  pre-commit 全天本地 chain，chain-phone 降级可选）——日常开发不再依赖
  Termux 资产。
- 但「在一台陌生设备上从零立起开发能力」仍无自举路径：工具链、依赖源、
  编译、热更全靠现成 Termux 环境。旧手机开机即此场景。

## 目标（验收判卷）

陌生设备（只装 na APK + 服务器可达）走通：

```
装 APK → 9022 通联 → 拉工具链包 → 拉源码 → 编出 libkfm_na.so
→ 热更换装 → 重启 na 生效
```

判卷 = 旧手机开机实测全链（C 档，实拍为凭）。这就是本项的终验收。

## 范围边界

- **舱内只编 Rust 核**：产出物 = 可热更的 `libkfm_na.so`（热更通道已有：
  hot/ 原子换装，BAR 系列成熟路径）。Java 皮变更极少且 APK 安装本来要
  人工点确认，不在舱内。
- 完整 chain（javac/aapt2/打包步）留在服务器与现有手机 Termux；舱内
  只保证「编得出 .so」+ 装完能自启（na 自己就是 smoke 探针）。

## 工具链包

- 内容：Termux 官方 rust + clang（aarch64 host → aarch64-linux-android
  target）+ **cargo vendor 依赖源**（离线可编，设备不需要碰 crates.io）。
- 服务器侧打包：`scripts/pack-toolchain.sh`（2026-09-23 立，未实跑）。
  **capture-first 策略**：不追 termux 仓库的 deb 依赖闭包（版本漂移、
  解析脆），直接快照手机里已在用的工具链（rust/clang 的 apt 依赖闭包
  → dpkg -L 文件全集 → tar 流回服务器重压缩 zstd + 版本清单）——保证
  产物 = 实证可编的那套。deb 直取留作「连快照源都没有」时的后备
  （MODE=fetch，未实现，挂账）。
- 体积预算：待 spike 实测（估压缩后 0.5~1GB）。

## 通道与落点

- 传输：9022 通道（`scripts/lib/na-ssh.sh` 全家，na 自持反连），大文件
  直接 `scp -P 9022`。
- 落点：na 私有目录 `files/` 下——exec 已放行（targetSdk 28 域降级，
  L3 实证）。工具链解压到 `files/toolchain/`，源码仓 `files/src/kfm-na/`。

## 驱动形态（分两版）

- **v1（文档+手敲）**：na 本地终端已有本地 PTY，按本档命令序列手跑通。
- **v2（解析页插件卡）**：走解析页插件契约（docs/active/解析页.md）加
  「编译舱」卡：工具链在不在/源码版本/一键编/构建日志尾/热更换装钮。
  v2 依赖插件契约适配新终端的既有挂账，不催。

## Spike（动工前必须先跑，数据回填本档）

1. 手机 Termux 里冷编 kfm-na release：耗时 / 峰值内存 / target 目录体积
   ——决定旧手机能不能扛（扛不住则降级，见风险）。**必须真机 Termux**
   （8022）：redroid 不算数——x86 服务器核多内存大，测不出手机级
   发热/内存墙；8022 被冻结时需用户点开 Termux 唤醒（na 侧 am 残废，
   唤不醒）。
   **✅ 已跑（2026-09-23，现役旗舰：6 核 / 15G RAM / rustc 1.97.1）**：
   冷编 rc=0，**3m01s / 173s 两趟互证**；峰值合计 RSS **1.6GB**、单进程
   峰值 **1.2GB**（最肥的 rustc）；target 目录 **496MB**；产物
   libkfm_na.so 6.9MB。**判读**：现役机余量巨大；旧手机的坎是单进程
   1.2GB——Android 对原生 RSS 无硬顶但低内存机会杀，4GB 级旧机须
   配 `CARGO_BUILD_JOBS=2` 压并发峰值并清后台。采样器教训：Termux 的
   ps 认 `rss=,comm=` 小写关键字，`PID,NAME` 大写直接报错静默归零。
2. `cargo vendor` 离线编验证：断网（或 --offline）冷编一把过。
   **✅ 已跑（2026-09-23）**：vendor rc=0，vendor 目录 **376MB**；
   `cargo check --offline --locked` rc=0 仅 **47s**。离线可编成立。
   （check 而非 build 全链：链接步与 spike 1 同源低风险，全链证明留
   编译舱首航。）
3. 工具链包重定位后在 na 私有目录 exec 冒烟：`rustc --version` + hello
   世界链接运行。**✅ 已跑通（2026-09-23）**：快照（251MB zst，sha256
   对账）经 9022 推进 na 私有目录，na 自有 zstd/tar 解压 1.1GB；
   **rustc/cargo/clang 三件套全跑起来**（LD_LIBRARY_PATH 指向包内 lib）；
   hello 世界 `-C linker=包内clang` 编译链接运行输出 `na-hatch-ok`。
   唯一缺件 = libicu（libxml2 链 libicuuc 却不申报，apt 闭包抓不到；
   补库后 LD_TRACE_LOADED_OBJECTS 全库扫描零缺失）——pack 脚本闭包
   已补种 libicu（BAR-137）。**三项 spike 全绿，编译舱可行性实证成立**。
   **pack 首跑已验证的副产物**：手机侧 apt 依赖闭包 19 包清单正确
   （rust/clang/llvm/lld/ndk-sysroot 等全在）。

## v1 首航（2026-09-23 ✅）

手机侧全链首编通过：**3m11s 出核**（`cargo build --release --offline
--locked`，src+vendor 解压至 `files/hatch/`，`.cargo/config.toml` 指
vendored-sources + 包内 clang 链接）。产出 6.86MB .so 已热更换装
（sha256 `397dd236…` 对账一致）。踩坑两枚：

1. **ETXTBSY（os error 26）**：build script 写完即 exec 偶发「Text file
   busy」，重跑即过——编译脚本必须可重入，别当成环境死刑。
2. **Termux 包装器 shebang 死路**：cc-rs 找 `aarch64-linux-android-clang`
   是 Termux 脚本，shebang 指 `/data/data/com.termux/...` 在 na 沙箱
   不存在 → EACCES。修 = `CC_aarch64_linux_android=<包内>/bin/clang`
   直指 clang-21（宿主即目标三元组，包装器只加 --target，可绕）。
3. **传输侧**：na 沙箱**没有 rsync**——rsync --append-verify 续推在
   9022 上必死（remote command not found，19 轮空转实录）。断点续传
   用 `tail -c +N | ssh cat >>`（每字节落盘即进度，杀几次都续得上）。

**build.sh 模板**（hatch/ 内，setsid 脱管防隧道抖动杀编译）：
`LD_LIBRARY_PATH=$TC/lib` + `PATH=$TC/bin:$PATH` + CC/AR 直指包内
+ CARGO_HOME/CARGO_TARGET_DIR 落 hatch 内。

## 风险与降级

- **老设备性能/存储/发热**：spike 1 数据说话。若真扛不住全量编，降级
  方案 = 服务器编好 .so、设备只热更——但那 9022 已够，本项价值退为
  「可选冗余」，不强求。
- SELinux / 私有目录 exec 限制随 Android 版本漂移： spike 3 先探。
- vendor 全量依赖的体积与更新成本：每次 Cargo.toml 变动要重打包，
  接受。
