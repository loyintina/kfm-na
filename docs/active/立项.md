## 一、定位

kfmv4 的 native 手机客户端。本质诉求：**一套内置 AI 的同居操作系统**——
把 Obsidian（文件/笔记）和命令行（服务器）用手机 UI 模式统一起来，
以远程连接服务器为基础，实现手机功能的扩展。

核心三件套（用户在用的全部，其余皆是赘余）：
1. **光球对话**——内置 AI 的居所
2. **tmux 里的 kimi code**——远程操作服务器
3. **文件树**——仿 Obsidian 手机端交互（kfmv4 tree-model 语义直接移植）

终局愿景：NA 成长到与 kfmv4 同等高度时，接管现在的 kfm 和数据。

## 二、架构三层

```
┌─────────────────────────────────┐
│  L2 覆盖层 UI（手势壳）           │  左缘手势→文件树 · 光球→对话面板 · 工具卡
│  （边缘手势由壳接管，与终端内容不冲突）│
├─────────────────────────────────┤
│  L1 网格眼睛 + 按键注入的手        │  AI 的感知与操作（见第四节）
├─────────────────────────────────┤
│  L0 终端底座（全屏）              │  alacritty_terminal + wgpu，
│                                 │  跑 tmux 里的 kimi code
└─────────────────────────────────┘
```

设计判断（2026-08-13 用户拍板）：
- **终端即中央页面**。kfmv4 的中央 HUD 是「浏览器里没有底座硬造底座」，
  手机上底座天然是终端。HUD 九宫格/卡片堆不继承
- **边缘手势是壳的，内容手势是终端的**——手机端十几年的成熟分界（Termux 同款）
- **浏览器转发路线否决**：终端是高频字节流，走 DOM 差分只会更慢

## 三、服务端复用（一行不动）

| 能力 | 协议（kfmv4 现有） |
|------|------------------|
| 终端 | terminal-pty ws（PTY 字节流双向） |
| AI 对话 | /ai/chat 系接口 |
| 文件树 | tree 接口（root/expand/操作） |

web 客户端保留给桌面，两端并存，互不杀。

## 四、眼睛与手 v2（native 红利）

kfmv4 的眼睛费劲的根源：xterm.js 把终端渲染成 canvas 位图，AI 看不见终端里的字。
native 版终端网格（`alacritty_terminal` 的 Grid）就在内存里——第几行第几列
什么字符直接可读：

- **眼睛 v2 = 网格快照 + 覆盖层矩形**（布局自算，比 DOM 采样精确一个量级）
- **手 v2 = 往 PTY 注入按键序列 + 触发壳手势**——没有「按错位置」这个 bug 类别
- AI 读 kimi code 屏幕 → 回话 → 注入操作，全闭环

设计思想来源：kfmv4 `docs/active/眼睛与手.md`（只读引用，不复制）。

## 五、工具卡

AI 调用工具 = 一等 UI 对象：edit 弹文件卡播编辑动画、grep 弹结果卡，
人也能召唤同样的卡用 AI 的工具。详见 `docs/active/工具卡.md`
（四个待拍板项定了才准实现）。

## 六、技术栈与零件

| 层 | 选型 | 理由 |
|----|------|------|
| 语言/打包 | Rust → aarch64-linux-android，cargo-apk | 服务器交叉编译，APK 几 MB |
| 窗口/输入 | winit（android-activity） | 软键盘/IME/手势，现成的 |
| 渲染 | softbuffer（软渲染，2026-08-13 改判） | wgpu 双后端在本机随机原生暴毙（判词见十）；终端负载本是 CPU 场景，零驱动依赖 |
| 终端模拟 | alacritty_terminal（crate） | 转义序列/网格/滚屏，最硬的骨头现成的 |
| 网络 | tokio + tokio-tungstenite | ws 客户端 |
| 树控件 | egui_ltreeview 或自绘虚拟列表 | MIT；文件树不是性能瓶颈 |

**明确不借**：Termux 本体及其 terminal-emulator 库（GPLv3 传染，且 Java 栈不搭）。

## 七、尖刺 1 验收标准（五条全过才算成，不达到不扩功能）

1. APK < 10MB
2. 冷启动到终端画面 < 1 秒（手机实拍）
3. 连上服务器 terminal-pty ws，`tmux attach` 进 kimi code，滚屏不输 Termux
4. 软键盘打字正常，中文输入法候选词正常
5. 协议解析与终端网格逻辑有服务器端无头测试（cargo test，不依赖手机）

已知的两颗雷（尖刺存在就是为了踩它们）：~~wgpu 的 Android Vulkan 兼容性~~
（2026-08-13 已踩爆：双后端随机原生暴毙，弃 GPU 转 softbuffer，判词见十）、
winit 中文 IME 的粗糙度（待踩）。踩完再决定后续切片做不做。

## 八、切片路线

1. **尖刺**：全屏终端 + ws + 键盘/IME（验收标准见上）
2. 左缘手势 → 文件树覆盖层（读 tree 接口，点文件 = 终端里打开）

4. 眼睛/手 v2 + 工具卡（网格眼睛、按键注入、工具即卡）

## 十、飞鸽传书（实拍回传通道，2026-08-13）

手机走蜂窝/WiFi NAT，服务器 adb 反连不回去，logcat 拿不到——C 档实拍
判卷缺证据链。通道设计：APK 既然能从服务器下载，就能向服务器回传。

- APK 侧 `src/report.rs`：panic 钩子 + boot 里程碑（android_main 进入 /
  resumed / wgpu 适配器 / 启动完成）HTTP POST 到
  `http://8.145.46.182/kfmv4/api/na-report`（nginx 80 反代，best-effort
  吞错——上报通道自己绝不能炸成二次事故）
- kfmv4 侧 `/na-report` 端点落盘 `/root/kfm-na/field-reports.log`
  （不挂 verifyLocalOrigin，手机本就是外部来源）
- 缘起：首版紫屏 APK 实拍闪退（2026-08-13），尸检打包无误（入口符号/
  清单/权限齐全），定为运行时 panic，建此通道抓现场
- 战果（同日）：回传里程碑把死亡行锁到 wgpu configure 段；结合开源调研
  定为 cargo-apk 默认 configChanges 不全 → OriginOS 启动注入配置变化 →
  Activity relaunch 杀使用中的 surface（android-activity#196，MIUI 同款）。
  修复 = `[package.metadata.android.application.activity] config_changes`
  补全 na-mainloop 全集（manifest 实测 0x40001ff0）
- **终审判词（同日晚）**：configChanges 修完仍死。升级仪器（每秒心跳 +
  死亡出口同步直报 + 裸窗对照组）后真相浮出——裸 winit 窗稳定（15s+），
  wgpu 一加进来就在 adapter/surface/configure 随机原生暴毙，Vulkan/GLES
  双后端同病、零 Rust panic，且历次「闪退」混着等待期手动退出被 exit(0)
  灭迹的假死。定性：本机 GPU 驱动栈与 wgpu 抽象层犯冲，非代码逻辑病。
  **用户拍板转 softbuffer 软渲染（a44f936），紫屏实拍一次通过，包体
  1.88MB→430KB**。GPU 路线留档后查（git 历史）
- 后路备忘：若 NativeActivity 还有第二个坑，生态共识是迁 GameActivity
  （Bevy 已默认，cargo-apk 被官方标 deprecated）——届时走 xbuild/gradle
开发方法论：**考题先行分三档**（A 纯逻辑考题先行+变异抽检 / B 胶水答案先行
考题钉住 / C 感官实拍判卷），细则见 AGENTS.md 方法论章——本文件的
尖刺五条验收标准即 C 档考题的首个实例。
第二档基建（信箱/语义巡逻/计数同步）等复杂度长出来再引——引什么看
kfmv4 对应机制的实证收益，不一股脑搬。
